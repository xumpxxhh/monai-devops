# 设计稿(Markdown)→ 高保真 HTML 原型

你的任务:拿到一份描述产品 / 页面的**设计稿(Markdown)**,把里面的「页面布局 / 文本线框图 + 信息架构 + 用户流程 + 交互说明」翻译成一套**能在浏览器直接打开、可点击跳转、真实数据真实图片、零占位符**的高保真 HTML 原型页面。这套原型是给人(产品、设计、客户、老板)点着看的「可演示样品」,它要回答的问题是:「这个东西做出来,长什么样、点起来什么手感」。

> **输入说明**:设计稿是一份 Markdown,**通常**会包含「需求概述 / 页面布局 + 文本线框图 / 用户流程(常用 Mermaid) / 关键交互说明 / 功能优先级(MVP 与迭代)」这几块,但具体小节名和结构可能因稿子而异。**不要假设它一定是某种固定模板**;按它实际写了什么去读,缺什么就在动手前问清楚。

核心理念(请真正理解,而不是机械套模板):

- **设计稿同时是「事实来源」和「意图来源」**。线框图里画了什么区块、放了什么控件、列了哪些字段、流程走哪条路径——这些是事实,要忠实落地;而需求里的目标用户、痛点、设计目标——这些是意图,决定了页面该有的气质和信息密度。两头都要读进去,不能只照着线框图摆控件却丢了它为谁、为何而做。
- **高保真,零占位符**。不允许 `Lorem ipsum`、灰块、`图片占位`、`xxx`。所有文案要是这个业务里真实、可信、具体的内容;所有图片用真实图(Unsplash / Pexels);数字、状态、时间要像真的。占位符会让评审瞬间出戏,等于白做。
- **视觉要有意图、不要模板感**。本 skill 默认走「大胆、个性化」的方向:每套原型先定一套**专属的设计基调**(配色 / 字体 / 布局概念 / 一个签名元素),让它一眼就属于这个产品,而不是「又一个默认蓝色中后台」。Ant Design 在这里只是**组件与交互的参考**(按钮该多大、表格怎么分页、表单怎么校验、危险操作怎么二次确认),**不是视觉上的紧身衣**——不要因为"要像 Antd"就把配色、版式做成千篇一律的默认样子。
- **可点击、能演示**。这是「原型」不是「截图」:菜单要能真跳转,主流程(用户流程里那条主路径)要能一步步点下去,弹窗能开能关,空 / 加载 / 错误状态摸得到。能点通的演示,胜过十张静态美图。
- **技术栈固定**,见下。不要自作主张换框架。

---

## 固定技术栈(不可更改)

- **结构**:HTML5(语义化标签)
- **样式**:Tailwind CSS,用 CDN 引入(Play CDN),通过 `tailwind.config` 注入这套原型的设计 token
- **脚本**:原生 JavaScript(不引 Vue / React),只用于:菜单跳转、弹窗开关、tab 切换、表单校验提示、状态切换等演示性交互
- **图标**:FontAwesome(CDN)
- **图片**:真实图片,优先 Unsplash / Pexels 的直链
- **基准**:高保真、零占位符;Ant Design 作为组件尺度与交互范式的参考

> 页面骨架模板、Tailwind+token 配置写法、各类常用组件(按钮 / 表格 / 表单 / 弹窗 / 标签 / 空状态 / Toast 等)的 Tailwind 实现片段、以及真实图片的取图方式,全部在 [`references/html-scaffold.md`](references/html-scaffold.md)。**动手写第一个页面前务必读它**,避免每页从零拼 HTML、避免组件风格不统一。

## 总体工作流

1. **读懂设计稿**:把 md 里的页面、信息架构、线框图、用户流程、交互说明、优先级读进脑子,理出「有哪些页面、它们怎么连、每页有哪些区块和控件、主流程怎么走、本期先做哪些」。
2. **确认落点 + 梳理页面清单**:这套原型放哪个目录?**每次都问用户**。同时把要产出的页面列成清单,和用户对齐(尤其哪些是优先 / 先做)。
3. **定设计基调(两遍法)**:先拟一套专属 token(配色 / 字体 / 布局概念 / 签名元素),再自我批判一遍「这是不是又一个默认中后台」,改掉模板化的部分,然后才动手。
4. **搭共享外壳 + 逐页实现**:设计一个贴合本产品的应用外壳(导航形态按产品定,不必非得"顶栏+左菜单"),每个页面一个独立 `.html` 复用这套外壳;把线框图里的控件翻译成真实组件 + 真实数据。
5. **注入真实内容与图片**:用业务真实文案填满,用真实图片,用 FontAwesome 图标。
6. **接通交互**:菜单真跳转、主流程能点通、弹窗 / 空 / 加载 / 错误状态可演示。
7. **自检**:对照清单过一遍。

下面逐步展开。

---

## 步骤 1:读懂设计稿(别急着写 HTML)

完整读一遍设计稿,把这几样东西理清楚——它们直接决定你要产出什么:

- **页面清单**:从页面布局 / 信息架构部分,数清楚有几个页面 / 视图。这决定你要产出几个 `.html`。
- **信息架构 / 跳转关系**:页面之间怎么连?谁是首页 / 主入口?这决定共享外壳里导航怎么摆、`index.html` 进来先看到哪页。
- **每页的区块与控件**:逐页读懂文本线框图——哪里是搜索框、哪里是表格(列是什么)、哪里是卡片组、哪里是筛选区、哪里是分页。线框图里 `[搜索框]` `[+ 新增]` `数据表格(列:姓名/角色/状态/操作)` 这类标注,就是你要落地成真实组件的清单。
- **主流程(用户流程)**:流程图里那条主路径,是这套原型「能点通的演示线」。把它落在哪几个页面、哪几个按钮上,记下来——步骤 6 要让它真的点得动。
- **关键交互**:二次确认、空状态、加载、校验时机这些,通常在交互说明里;它们决定步骤 6 要做哪些状态与反馈。
- **范围 / 优先级**:若设计稿区分了 MVP 与后续迭代(或标了优先级),**先把优先级高的页面和功能做扎实**,低优先的可以先放轻(做个入口或留空态),除非用户要求全做。

> 如果设计稿信息不全(比如线框图模糊、没说字段)、结构和上面不完全对应、或某页你拿不准要不要做,**先问一句**,别凭空发挥编出一堆和设计稿对不上的东西。

---

## 步骤 2:确认产出位置 + 梳理页面清单

- **产出位置每次都问用户**,不要擅自塞目录。可以给建议(如「放在 `prototype/<功能名>/` 下,每个页面一个 html,加一个 index.html 入口,可以吗?」)让用户确认。
- **目录约定**(建议):一套原型放同一个目录;`index.html` 作为入口(指向主页面或一个总览导航页);其余页面见名知意命名(`document-list.html`、`upload.html`…);如有自定义的公用样式 / JS,放同目录的 `assets/`(Tailwind 用 CDN 时通常不需要)。
- **把页面清单列给用户对齐**:简短列出「我准备产出这些页面:① 文档列表(先做)② 上传(先做)③ 问答(先做)④ 设置(后续,先留入口)……」,让用户确认范围,避免做多了或漏了。

---

## 步骤 3:定设计基调(两遍法,这步决定它像不像"作品")

这是把原型从"能用的默认模板"拉到"有记忆点的样品"的关键一步。**先想清楚要做成什么气质,再写代码**,否则很容易顺手做成默认蓝色中后台。

把自己当成一家小工作室的设计主理人:客户花钱买的是一个**只属于他这款产品**的视觉点子,而不是随便套个模板就能交的东西。独特性来自这款产品自己的世界——它的业务、用户、所处行业的材质与语汇,就是与众不同的选择的来源。

**先锚定主题**:这套原型服务的是什么产品、什么人、这页最主要的一件事?从需求里把它说清楚(比如「给运维工程师看的管道告警监控,核心是第一眼抓住异常」)。

**第一遍——拟一套专属 token**(在脑子里或简短写给用户):

- **配色**:4~6 个有名字的 hex。定一个**贴合业务的主色**(不要条件反射用 Antd 默认蓝 `#1677ff`,除非这个业务确实适合冷静的蓝),配中性灰阶、背景、以及成功 / 警告 / 危险的语义色。
- **字体**:正文一套(中文常用系统字体栈),需要的话给标题 / 数字一套更有性格的搭配;定一个清晰的字号 / 字重层级。让排版本身成为有记忆点的一部分,而不只是中性的文字容器。
- **布局概念**:这套产品的外壳长什么样?**不要默认"顶栏 + 左菜单"**——根据产品想清楚:是经典中后台(侧边导航)?是仪表盘 / 数据大屏(模块化网格)?是工作台(顶部 tab)?用一句话 + 简单 ASCII 描述定下来。
- **签名元素**:这套原型最值得被记住的一个细节是什么(一种状态徽标的处理、一组数据可视化的风格、卡片的层次、空状态的语气……)。把张力集中在这一个点上,其他地方保持克制。

**第二遍——自我批判**:回头看这套 token,如果它读起来像"我对任何同类页面都会产出的默认答案",就改掉,并说一句你改了什么、为什么。当下 AI 生成的设计很容易撞进几种套路——暖米色背景 + 衬线大标题 + 赤陶色;纯黑底 + 一个荧光绿 / 亮红;或报刊式细线网格、零圆角、密排多栏——它们对某些主题是合理选择,但若**与产品无关地反复出现**,那就是偷懒的默认而非有意的选择。**只有确认这套基调是为这份稿子做的选择,才开始写代码。**

> B 端 / 中后台提醒:这类产品的"个性"通常不在花哨的 hero,而在**信息密度的把控、状态 / 数据的可视化、克制而精确的间距与层级**。大胆 ≠ 堆装饰;把一个签名元素做到位,其余安静利落,往往比满屏特效更高级。离场前像 Chanel 说的那样照照镜子、摘掉一件多余的"配饰"。质量底线顺手带上:响应式能缩到窄屏、键盘焦点可见、尊重 `prefers-reduced-motion`。

把定下来的 token 写进 `tailwind.config`(见 scaffold 参考),后面每个颜色、字号都从这套 token 取,保证全套页面统一。

## 步骤 4:搭共享外壳 + 逐页实现

### 4.1 设计并复用「应用外壳」

按步骤 3 定的布局概念,做一个贴合本产品的外壳(导航 + 全局信息区)。每个页面 `.html` 都包含同一套外壳标记,**菜单项用真实 `<a href="xxx.html">` 指向对应页面**,当前页高亮。这样每个 html 都能独立打开、又能互相跳转,天然就是可点击原型。

- 外壳形态服从产品,不必拘泥固定式样;但同一套原型里**所有页面外壳要一致**(同样的导航、同样的顶部信息、同样的 token)。
- `index.html` 作为入口:可以是主页面本身,也可以是一个简洁的「原型总览 / 导航页」,列出所有页面入口,方便评审从这里点进每一页。

> 外壳标记会在每个页面重复——这是为了让每个 html 能独立打开,可接受。把外壳做成一段清晰、好复制的结构(见 scaffold 参考),逐页复用并只改"当前页高亮 + 主内容区"。

### 4.2 把线框图翻译成真实页面

逐页对着线框图落地。线框图是抽象骨架,你要把它"长出血肉":

- **控件 → 真实组件**:`[搜索框]`→ 真实的带图标输入框;`数据表格(列:…)` → 真实表头 + **多行真实数据**;`[筛选区]` → 真实的下拉 / 日期 / 标签筛选;`[分页]` → 真实分页器。组件的尺度、交互范式参考 Antd(见 scaffold 的组件片段),视觉按你的 token 来。
- **重复结构填真实数据**:表格行、卡片列表、图例等"长一样、数据不同"的结构,要给出**若干条互不相同的真实数据**(8~12 行表格、5~8 张卡片之类),不要只放一行示意。数据要符合业务语境(真实的名字、状态、时间、数值)。
- **主次与留白**:线框图里占地大的核心区(主表格 / 主图表),在真实页面里也要有最大的视觉权重;次要区(筛选 / 辅助信息)克制。用 token 的间距体系拉开层级。
- **图表 / 可视化**:线框图里若有图表区,用简单方式实现可视化(纯 CSS / SVG / 内联 `<canvas>` 轻量画,或一段极简 JS),保证"看起来是真实的图表"。不必引重型图表库——这是原型,重点是形与神到位。
- **响应式**:用 Tailwind 的响应式类让页面能从宽屏缩到窄屏不破版;核心区优先保证。

## 步骤 5:注入真实内容与图片(零占位是硬指标)

- **文案**:所有标题、标签、菜单、按钮、表格数据、提示语,都写成这个业务里**真实、具体、可信**的中文内容。想象真实系统会显示什么就写什么。避免 `标题1`、`内容内容`、`xxx`。文案是设计材料而非装饰:按用户认得的说法命名(「通知」而不是「webhook 配置」),用主动语态写动作(`保存` 而不是 `提交`),同一动作从按钮到反馈保持同名。
- **图片**:需要图片处(头像、封面、缩略图、空状态插画、用户上传示例…)用**真实图片直链**(Unsplash / Pexels)。取图方式见 scaffold 参考。给 `alt`。
- **图标**:用 FontAwesome,选**语义贴切**的图标(上传用 `fa-upload`、告警用 `fa-triangle-exclamation`),不要乱套。
- **数字与状态**:数值、百分比、时间、状态标签要有真实感和内部一致性(总数和列表条数对得上、时间是近期合理日期)。

---

## 步骤 6:接通交互(让它"能点")

按设计稿的用户流程和关键交互,用原生 JS 把演示线接通。**不必实现真实业务逻辑**,目标是"点起来像真的、能把主流程演示完":

- **导航跳转**:菜单 / 关键按钮用真实链接或 JS 跳到对应 `.html`,让那条主路径能一页页点下去。
- **弹窗 / 抽屉 / 二次确认**:线框图里的"新增 / 编辑弹窗"能开能关;危险操作(删除 / 提交)按关键交互说明做二次确认。
- **状态可演示**:把关键交互里提到的**空状态、加载中、错误 / 校验失败**做出来,并提供一种能看到它的方式(比如表格上方放一个"切换演示状态"的小控件,或单独留一个空态示例)。把失败和空态当作给方向的时机,而不是堆情绪:错误要说清出了什么、怎么修,空状态是一句邀请用户行动的引导,而不是一句道歉。这些状态最能体现体验考量,别省。
- **即时反馈**:按设计稿,搜索是输入即筛还是点按钮筛、表单是失焦校验还是提交校验,照着做;操作成功给 Toast / 提示(按钮文案和反馈文案要一致:`发布` → `已发布`)。
- **JS 保持轻**:只服务于演示性交互,不要引入复杂状态管理或真实请求。

## 收尾自检清单

交付前对照过一遍:

- **页面齐 & 能互通**:设计稿里(优先 / 先做)的页面都产出了对应 `.html`;`index.html` 入口可用;菜单 / 主流程能真实点击跳转,主路径能从头点到尾。
- **零占位符**:全篇无 `Lorem`、无灰块、无 `xxx` / `图片占位`;文案真实具体,图片是真实直链且能加载,图标语义贴切。
- **忠实于设计稿**:线框图里的区块、控件、表格字段、筛选项都落地了;主流程与关键交互(空 / 加载 / 错误 / 二次确认)都有对应实现;没有"线框图画了却没做"或"凭空多出来一堆设计稿没有的东西"。
- **视觉有意图、非模板**:有一套专属 token 且全套统一;主色 / 版式 / 签名元素是为这份稿子做的选择,不是默认中后台套路;Antd 只作了组件 / 交互参考,没把视觉做成千篇一律。
- **技术栈合规**:HTML5 + Tailwind(CDN)+ 原生 JS + FontAwesome;没有混入 Vue / React 或别的框架;`tailwind.config` 注入了 token。
- **质量底线**:能缩到窄屏不破版;键盘焦点可见;动画尊重 `prefers-reduced-motion`。
- **产出位置已和用户确认**,文件名见名知意。

完成后,简要告诉用户:产出了哪些页面、入口在哪、定了怎样的设计基调(主色 / 签名元素是什么、为什么这么选)、主流程能怎么点着演示、以及哪些先做了、哪些暂时留了入口 / 空态。
