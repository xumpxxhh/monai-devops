# CI/CD 与 AI Agent 共用内核增强前置提案（待评审）

## 1. 提案目的

CI/CD 和 AI Agent 虽然是两条不同产品路线，但都依赖同一组通用执行能力：

- 能够长期运行、暂停、恢复和取消的 Run；
- 可恢复、可审计、可重放的执行状态；
- 可靠的任务调度、资源控制和失败处理；
- 统一的步骤/工具输入输出契约；
- 完整的生命周期事件与执行轨迹；
- 明确的权限、预算和副作用边界；
- 可扩展但不被具体领域绑死的插件执行接口。

如果两条分支各自建设这些能力，容易出现状态模型、事件模型、重试语义和执行边界分裂。因此建议先形成一条共享内核演进路线，再在其上派生 CI/CD 和 Agent 能力。

## 2. 目标与非目标

### 2.1 目标

建立一个能够同时承载确定性工作流和受控动态执行的通用执行内核，为下游领域提供稳定基础：

```text
Shared Execution Core
    ├── CI/CD Domain
    └── AI Agent Domain
```

内核应负责通用执行语义，不负责决定某个领域的产品模型。

### 2.2 非目标

本文不决定：

- CI/CD 的 Pipeline、Runner、制品和部署模型；
- Agent 的模型供应商、长期记忆和多 Agent 产品形态；
- 最终采用何种队列、数据库、对象存储或部署平台；
- 是否保持当前所有 API 和数据结构不变；
- 具体重构排期和人员投入。

## 3. 当前内核需要先解决的共性问题

当前 `core-engine` 已有 DAG、资源、Run 控制、嵌套工作流和事件能力，但仍存在一些不适合直接承载两条生产路线的共性边界：

1. 执行状态主要是进程内状态，服务重启和跨进程恢复语义不足；
2. 任务调度、重试、取消和重复投递的幂等边界还需统一；
3. Run、Step、Attempt、子执行和事件之间的关联模型需要稳定化；
4. 事件流已能支持实时展示，但还需要可靠落库、顺序、offset 和回放语义；
5. 插件执行契约尚未完整表达权限、资源、超时、副作用和能力要求；
6. 资源池目前更接近进程内调度，需要演进为可扩展的资源/能力调度抽象；
7. 长任务等待人工输入、外部事件或恢复点的状态模型尚不完整；
8. 大型日志、轨迹、结果和上下文不应全部进入单个 Run JSON；
9. 失败分类、重试策略和终态原因需要形成跨领域统一语义；
10. 执行隔离边界需要从“宿主调用插件”演进为可接入外部 Executor/Runner 的协议。

## 4. 建议的共用内核增强方向

### 4.1 稳定的执行对象模型

建议评审是否将执行对象明确拆为：

```text
WorkflowDefinition
    └── Run
          └── Job
                └── Attempt
                      └── Step / Tool Execution
```

候选语义：

- `Run`：一次顶层工作流执行；
- `Job`：一个可调度的执行单元，可以是步骤、Agent 迭代或外部任务；
- `Attempt`：同一 Job 的一次实际尝试，重试不得覆盖历史；
- `Step / Tool Execution`：具体插件、工具或内置步骤执行。

这组对象不代表必须新增同名表，但需要统一标识、状态、父子关系和审计语义。

### 4.2 持久化状态机与恢复

内核需要明确：

- 哪些状态是权威状态；
- 哪些状态可以从事件重建；
- 哪些状态只存在于执行器内存；
- 服务重启后如何恢复；
- Executor 失联后如何重新领取；
- 取消、暂停和恢复在跨进程环境下如何生效。

建议引入 checkpoint 和 lease 概念：

- checkpoint 记录可恢复边界；
- lease 表示某个 Executor 暂时拥有执行权；
- lease 过期后任务可被重新领取；
- 重新领取必须依赖幂等键和 Attempt 语义。

### 4.3 统一调度与幂等语义

需要统一以下行为：

- 业务失败是否重试；
- 基础设施失败是否重试；
- 取消后是否允许后台执行继续；
- 超时后资源何时释放；
- 重复投递如何避免重复副作用；
- 失败后从头重跑还是从 checkpoint 继续；
- 子执行失败如何向父执行传播。

建议所有可重试执行都显式声明：retry policy、idempotency key、timeout、cancellation mode、side-effect level 和 recovery strategy。

### 4.4 Executor 抽象与执行边界

当前插件执行器可以保留为本地 Executor，但内核需要抽象出统一执行接口，以支持本地进程、容器、远程 Runner、Agent Tool 和人工任务等执行器。

候选协议：

```text
submit → lease → start → heartbeat → event/log → complete
                         └────────────→ cancel / pause
```

执行隔离、网络、文件系统和 Secret 注入可以由具体 Executor 实现，但权限和 capability 声明应由内核统一承载。

### 4.5 统一事件与轨迹模型

建议将实时事件、持久化事件和审计轨迹建立统一模型，至少包含 execution/run、job/attempt、父执行、sequence/offset、事件类型、actor/executor、时间戳、correlation id 和 payload version。

事件需要支持实时订阅、断线续传、按 offset 回放、终态重建、审计查询以及调试和测试中的执行重放。

### 4.6 状态、上下文和大对象分层

建议区分结构化 Run/Job 状态、执行事件和审计、日志与大结果、临时上下文以及外部业务状态。数据库保存权威状态和引用，对象存储保存大对象，避免把完整日志、轨迹和上下文塞进单个 Run JSON。

Context 引用可以继续保留，但需要明确引用的是结构化状态、事件结果还是外部对象引用。

### 4.7 能力、资源和权限抽象

资源池不应只表示固定数量的槽位，还可以统一表达并发额度、模型或硬件额度、外部系统访问权、文件/网络/Secret capability，以及租户、项目和执行身份。

建议将“资源可用性”和“权限可用性”分开建模，但使用统一的调度约束接口。

### 4.8 可靠的等待与唤醒

内核需要支持可持久化的 `WAITING` 状态、唤醒条件、超时和取消，覆盖等资源、外部事件、人工审批、模型回调和定时唤醒等场景，而不是依赖进程内 Promise 长时间挂起。

### 4.9 统一可观测性与成本计量

内核应统一产出状态转换、排队/执行/恢复耗时、资源利用率、重试/取消/失败原因、事件延迟和配额消耗接口。CI 的制品指标或 Agent 的 Token 指标由下游领域补充，但挂接到统一的 Execution/Run 维度。

## 5. 建议的前置实施顺序

> 以下仅表示依赖顺序，不代表已批准的排期。

### Core-0：语义盘点与兼容边界

- 盘点现有 Workflow、Run、Step、事件和插件契约；
- 固化状态、失败、取消、暂停和重试语义；
- 明确旧工作流 JSON 的兼容策略；
- 输出状态机、事件字典和迁移原则。

### Core-1：执行对象与事件模型

- 稳定 Run/Job/Attempt/Execution 标识；
- 统一父子执行关系；
- 事件顺序、版本、offset 和回放；
- 失败原因、终态和取消原因标准化。

### Core-2：可靠调度与恢复

- lease、heartbeat、checkpoint；
- 持久化等待队列；
- 重复投递与幂等键；
- 服务重启和 Executor 失联恢复；
- 跨进程 pause/resume/cancel。

### Core-3：Executor 与能力边界

- 本地 Executor 适配；
- 远程 Executor 协议；
- capability、资源和权限声明；
- 超时、取消和副作用治理；
- 大对象、日志和轨迹引用化。

### Core-4：稳定性验证

- 故障注入和恢复测试；
- 并发、长任务和大事件量测试；
- 事件回放一致性测试；
- 幂等和重复执行测试；
- 兼容旧工作流的回归测试。

只有 Core-0 至 Core-4 的目标和退出标准评审通过后，才建议分别推进 CI/CD 或 AI Agent 的领域能力。

## 6. 与两条路线的分叉关系

共享内核只提供共同的执行基础，分叉后由各领域自行增加模型：

```text
                 Shared Core
                /            \\
               /              \\
          CI/CD Domain     Agent Domain
          - Pipeline        - Model
          - Runner          - Tool
          - Artifact        - Memory
          - Deployment      - Approval
```

### CI/CD 分支侧重

- Pipeline、Repository、Environment、Deployment；
- Runner Pool、制品、缓存和发布回滚；
- Webhook、分支策略和供应链治理。

详见：[企业级 CI/CD 推演](../ci-cd-engine/enterprise-ci-cd-roadmap-draft.md)。

### Agent 分支侧重

- Agent、Model、Tool、Memory；
- 预算、轨迹、策略和人工审批；
- 单 Agent、多 Agent 和长期任务。

详见：[AI Agent 推演](../agent-engine/ai-agent-execution-engine-roadmap-draft.md)。

两条分支不得把各自领域的专有概念反向写入共享内核，除非经过共用抽象评审。

## 7. 主要风险

| 风险 | 说明 | 建议控制方式 |
| ---- | ---- | ------------ |
| 过度抽象 | 为尚未验证的 CI/Agent 需求提前设计复杂内核 | 先做最小通用语义，领域需求通过 RFC 反推 |
| 兼容性破坏 | 状态机和事件模型变化影响现有前后端 | 版本化、迁移层和回归测试 |
| 可靠性不足 | 只增加抽象，没有真正解决恢复和幂等 | 故障注入作为退出条件 |
| 内核膨胀 | 把制品、模型、记忆等领域能力塞进 core-engine | 保持领域模块和 Executor 插件化 |
| 双分支漂移 | CI 和 Agent 各自修改共享语义 | 共享 RFC、ADR 和兼容性测试 |
| 重构周期过长 | 前置内核项目迟迟不产生可验证价值 | 每个 Core 阶段设最小可用闭环和停止条件 |

## 8. 待评审问题

1. 哪些能力必须进入 `core-engine`，哪些应留在领域包或 Executor？
2. Run/Job/Attempt/Execution 是否需要成为正式持久化模型？
3. 事件存储是否继续以 PostgreSQL 为主，还是引入独立事件系统？
4. 是否接受至少一次投递，并要求所有副作用执行声明幂等语义？
5. checkpoint、lease 和等待状态的权威来源是什么？
6. 本地插件执行和远程 Executor 是否共用同一协议？
7. capability、资源和权限是否需要统一抽象？
8. 旧 Workflow JSON 的兼容期限和迁移方式是什么？
9. Core-0 至 Core-4 的验收指标如何定义？
10. 如何防止 CI/CD 与 Agent 分支对共享内核产生不可控分叉？

## 9. 建议的评审产物

在进入具体开发前，建议形成：

1. 共用执行语义 RFC；
2. Run/Job/Attempt/Execution 状态机；
3. 事件类型、版本和回放规范；
4. Executor/lease/checkpoint 协议；
5. 插件与能力声明规范；
6. 旧工作流兼容与迁移方案；
7. 故障注入和恢复测试计划；
8. CI/CD 与 Agent 分支的接口边界清单。

评审通过后，应将确认结论沉淀为 ADR/RFC，并分别更新两条下游路线的状态；在此之前，本文及下游文档中的相关内容均只应视为推演假设。
