## 1. 推演目标

评估当前项目能否作为企业级 CI/CD 流水线引擎的演进基础，并回答以下问题：

1. 当前哪些能力可以保留和复用？
2. 从 CI PoC 到生产级平台还缺少哪些关键能力？
3. 哪些架构边界需要优先调整？
4. 如果继续演进，可以按什么阶段推进？
5. 正式立项前还需要完成哪些评审和验证？

本文暂不决定：

- 是否自研完整 CI/CD 平台；
- 是否替代 Jenkins、GitHub Actions、GitLab CI、Tekton 等现有系统；
- 最终采用 Docker、Kubernetes Pod、虚拟机还是混合 Runner；
- 最终选用哪一种消息队列、对象存储、密钥系统或策略引擎；
- 具体里程碑、人员投入与交付时间。

## 2. 当前基础与初步判断

### 2.1 当前已有能力

当前仓库已经具备以下可复用基础：

- DAG 工作流、依赖调度、并行执行、条件跳过和失败传播；
- 插件契约、配置校验、结果描述、日志与协作式取消；
- 资源槽位、Run 生命周期、暂停/恢复/取消；
- 工作流组合、子工作流和循环执行；
- Run 快照、生命周期事件、PostgreSQL 持久化与实时推送；
- React 工作流编辑器、运行详情、插件与资源管理界面；
- checkout、文件注入、shell 执行组成的最小 CI Pipeline PoC；
- pnpm workspace、Turbo、测试与工程质量脚本。

### 2.2 初步可行性判断

当前项目适合作为企业内部 CI/CD 引擎的技术底座继续演进，但还不能直接作为生产级 CI/CD 平台使用。

粗略判断：

| 目标 | 初步判断 | 说明 |
| ---- | -------- | ---- |
| 作为编排与插件技术底座 | 可行性较高 | 核心抽象与依赖边界基本合理 |
| 服务可信内部仓库的小规模 CI | 有条件可行 | 需要先完成 Runner 隔离、可靠任务投递和基础权限 |
| 企业级生产交付平台 | 可行但投入较大 | 需要执行面、安全、可靠性、审计和 CI/CD 领域模型的系统建设 |
| 全面替代成熟通用 CI/CD 产品 | 暂不判断 | 需结合组织规模、差异化价值和长期维护成本评审 |

当前成熟度短板主要不在 DAG 编辑器，而在：

- 不可信代码的隔离执行；
- 服务重启、Runner 失联等异常下的可靠恢复；
- 身份、权限、密钥、审计和供应链安全；
- 制品、缓存、环境、部署、审批等 CI/CD 领域能力；
- 多实例、高可用、容量治理和多租户隔离。

## 3. 建议保留的设计

以下设计方向具有继续复用的价值：

1. **编排内核与插件契约分离**  
   `core-engine` 负责工作流语义，插件负责业务能力，有利于扩展构建、测试、扫描和部署步骤。

2. **DAG、资源池与生命周期事件作为核心抽象**  
   这些是流水线引擎的基础能力，可继续扩展重试、超时、矩阵、审批和环境锁。

3. **工作流可组合化**  
   子工作流可进一步演变为企业级流水线模板，例如 Java 标准构建、镜像发布和生产部署基线。

4. **Run 快照与事件持久化**  
   可以作为审计、故障恢复和执行追踪的基础，但需要补齐明确的恢复和幂等语义。

5. **插件只依赖 plugin-sdk 的依赖方向**  
   该约束有助于维持插件独立性，应继续保留。

## 4. 核心架构推演

### 4.1 首要边界：控制面与执行面分离

当前 PoC 允许服务端在 Run 工作区中执行 shell。该模式适合本地验证，不适合直接承载生产环境中的不可信代码。

候选架构如下：

```text
Web / API
    │
    ▼
Control Plane
工作流、权限、审批、调度、状态
    │
    ▼
Durable Queue
任务投递、租约、重试、心跳
    │
    ▼
Runner / Agent
容器、Kubernetes Pod、VM 或专用机器
    │
    ├── Workspace
    ├── Cache
    ├── Artifact
    └── Secret Injection
```

候选职责划分：

- Control Plane 决定执行什么、何时执行、谁有权限执行；
- Durable Queue 承担可靠投递、租约、超时和重新领取；
- Runner 在隔离环境中执行任务并回传日志、事件和结果；
- PostgreSQL 保存权威状态和审计元数据；
- 对象存储保存日志、缓存和制品正文；
- 密钥系统提供短期、按需、可审计的 Secret 注入。

此处尚未决定具体中间件和部署形态。

### 4.2 插件执行位置

需要评审插件是在 Control Plane 还是 Runner 中执行。候选方案是按能力分类：

- 控制类插件：在 Control Plane 执行，例如审批状态读取、元数据操作；
- 构建类插件：在 Runner 执行，例如 checkout、shell、测试、打包；
- 部署类插件：根据目标环境和权限模型决定在受控 Runner 或专用执行器中执行。

插件可能需要新增以下声明：

- execution target；
- 所需能力和权限；
- 网络策略；
- Secret 使用范围；
- 资源需求；
- 是否支持重试和幂等；
- 插件版本及兼容范围。

## 5. 生产级能力缺口

### 5.1 执行隔离

- 容器、Kubernetes Pod 或虚拟机隔离；
- CPU、内存、磁盘和执行时间限制；
- 非 root、只读基础镜像与最小权限；
- 网络访问策略和出站控制；
- Run 工作区自动回收；
- 不可信 Fork/PR 的独立安全域；
- Runner 不可直接访问 Control Plane 数据库。

### 5.2 调度可靠性

- 持久化任务队列；
- Runner 注册、心跳、租约与失联检测；
- 至少一次投递及相应幂等设计；
- 服务重启后的 Run 恢复；
- cancel/pause 的跨进程一致性；
- 基础设施失败与业务失败的重试边界；
- 并发组、环境锁和容量配额；
- 多调度实例下的 leader election 或无主化抢占。

建议评审是否将执行记录明确拆分为：

```text
Workflow → Run → Job → Attempt → Step
```

其中重试产生新的 `Attempt`，不覆盖历史执行记录。

### 5.3 身份、权限与审计

- OIDC、SAML 或 LDAP 登录；
- 组织、项目、仓库、环境级 RBAC；
- 编辑、执行、审批和生产部署权限分离；
- Runner 注册、轮换和吊销；
- API Token 与 Service Account；
- Webhook 签名校验、防重放和来源限制；
- 不可抵赖的操作与部署审计日志。

### 5.4 密钥管理

- 接入 Vault、云 Secret Manager 或 Kubernetes Secret；
- Secret 不进入工作流 JSON、Run 快照和普通 API 响应；
- 日志自动脱敏；
- Secret 按项目、环境、步骤和身份授权；
- Fork/PR 默认无法读取受保护环境 Secret；
- Secret 使用行为进入审计记录。

### 5.5 CI/CD 领域模型

通用 DAG 之上可能需要新增：

- Repository / Revision；
- Pipeline / PipelineVersion；
- Trigger；
- Environment；
- Deployment；
- Artifact；
- Cache；
- Approval；
- Variable / Secret；
- RunnerPool；
- ConcurrencyGroup。

领域模型需要支持回答：哪个提交、通过哪条流水线、由谁批准、部署到了哪个环境、产出了哪些制品，以及如何回滚。

### 5.6 制品、缓存与日志

- 对象存储承载大日志、构建缓存和制品；
- 日志分片、offset、断线续传、归档与留存；
- cache key、fallback、过期和配额；
- 制品校验和、签名、访问控制和生命周期；
- 镜像摘要、SBOM 和 provenance 元数据。

### 5.7 可观测性与运维

- OpenTelemetry Trace；
- Prometheus 指标及容量看板；
- 结构化日志与统一 correlation ID；
- 队列等待时间、执行时间、失败率和 Runner 利用率；
- SLO、告警、灾备和恢复演练；
- WebSocket 继续用于 UI 实时展示，但不作为可靠事件总线。

## 6. 候选演进阶段

> 以下阶段仅用于表达依赖关系和建议顺序，不代表已经批准的 Roadmap 或排期。

### 阶段 A：技术验证与边界定型

目标：验证控制面/执行面分离的关键假设。

候选内容：

- 定义最小 Runner Protocol；
- 从 Server 进程中拆出一个独立 Runner；
- 完成任务领取、心跳、日志、取消和结果回传；
- 使用容器执行可信测试任务；
- 验证服务重启、Runner 失联和重复投递；
- 输出安全威胁模型和容量基线。

建议退出条件：能够证明任务不会因单个 Server/Runner 异常而静默丢失，且执行环境具备最小隔离。

### 阶段 B：可控的内部 CI

目标：支持可信内部仓库的小范围生产试用。

候选内容：

- Durable Queue、租约、Attempt 与恢复；
- Docker Runner 与资源限制；
- Git Webhook 触发；
- 对象存储日志、制品与缓存；
- 基础 OIDC、项目 RBAC 和审计；
- 步骤超时、重试和手动重跑；
- Runner Pool 和标签匹配。

建议退出条件：满足试点团队定义的可靠性、安全性和可观测性门槛，并完成故障演练。

### 阶段 C：企业交付平台

目标：覆盖受控环境中的构建、发布和部署。

候选内容：

- Kubernetes Runner 与弹性伸缩；
- Environment、Deployment、Approval 和并发锁；
- Vault/Secret Manager；
- 流水线模板、策略和合规审计；
- 灰度、回滚和部署历史；
- 多租户配额与高可用 Control Plane。

### 阶段 D：平台生态与供应链治理

目标：增强跨团队复用、开放扩展和软件供应链安全。

候选内容：

- Pipeline as Code；
- 插件版本、签名、权限清单和兼容策略；
- 自托管 Runner；
- 矩阵任务和动态工作流；
- OPA/Cedar 等策略能力；
- SBOM、SLSA、镜像签名和 provenance；
- 多 SCM、多制品库和多云适配。

## 7. 候选代码边界

如控制面/执行面分离方向获得认可，可评估新增以下模块：

| 候选模块 | 候选职责 | 状态 |
| -------- | -------- | ---- |
| `packages/runner-protocol` | 任务领取、心跳、日志、取消、结果回传协议 | 待评审 |
| `apps/runner` | 工作区、容器/进程执行、缓存、制品和 Secret 注入 | 待评审 |
| `packages/ci-domain` | Pipeline、Job、Attempt、Artifact、Environment、Deployment 等领域模型 | 待评审 |

现有模块的候选定位：

- `packages/core-engine`：负责纯编排和状态机，不直接执行不可信进程；
- `apps/server`：作为 Control Plane；
- `packages/plugin-sdk`：描述步骤能力、配置、结果和执行要求；
- `plugins/*`：控制类能力或 Runner Task 的业务封装；
- PostgreSQL：权威状态和审计元数据；
- Durable Queue：任务传输和租约；
- S3/MinIO 类对象存储：日志、缓存和制品。

这些模块名称与职责均为推演占位，不是已批准设计。

## 8. 主要风险

| 风险 | 说明 | 建议验证方式 |
| ---- | ---- | ------------ |
| 范围失控 | CI/CD 产品面远大于 DAG 引擎 | 先定义目标用户和不做清单 |
| 安全边界不足 | shell、源码和 Secret 都属于高风险执行面 | 威胁建模、红队测试、隔离 PoC |
| 分布式一致性复杂 | 重试、取消、失联恢复容易产生重复副作用 | Attempt、租约、幂等测试和故障注入 |
| 插件边界模糊 | 控制逻辑与执行逻辑混在同一插件模型中 | 评审执行位置和 capability 模型 |
| 自研成本低估 | Runner、缓存、制品、权限和生态维护成本长期存在 | 与集成现有 CI/CD 产品做成本对比 |
| 迁移兼容性 | 当前工作流模型未必适合 Pipeline as Code | 设计版本化与兼容层 PoC |
| 运维复杂度 | 高可用控制面和弹性 Runner 引入新基础设施 | 容量、SLO、灾备和运维人力评估 |

## 9. 待评审问题

正式形成路线前，至少需要明确：

1. 目标是编排引擎、内部 CI 平台，还是完整 CI/CD 产品？
2. 首批用户和必须解决的差异化问题是什么？
3. 是否允许执行外部或不可信仓库代码？
4. 首选执行环境是 Docker、Kubernetes、虚拟机还是混合模式？
5. Control Plane 和 Runner 的信任边界如何划分？
6. 需要支持哪些 SCM、制品库、部署目标和密钥系统？
7. 可靠性目标、并发规模、日志量和制品量是多少？
8. 多租户、数据隔离、合规和审计要求是什么？
9. 哪些能力适合自研，哪些能力应集成现有系统？
10. 当前工作流 JSON 是否继续作为主要定义格式，是否引入 Pipeline as Code？
11. 插件如何版本化、签名、授权和升级？
12. PoC 进入内部试点的安全与可靠性退出门槛是什么？

## 10. 建议的下一步评审产物

若决定继续评估，建议先产出以下材料，而不是直接进入全面开发：

1. 产品定位与“不做清单”；
2. Control Plane / Runner 威胁模型；
3. Runner Protocol 最小 RFC；
4. Run / Job / Attempt 状态机与失败恢复语义；
5. 执行隔离 PoC 与故障注入报告；
6. 目标规模和容量估算；
7. 自研、集成现有系统、二次开发三种方案的成本对比；
8. 阶段 A 的验收标准和停止条件。

评审完成后，应将已确认结论单独沉淀为 ADR/RFC，并更新本文状态；未确认内容继续保留为假设，不应直接作为实现依据。
